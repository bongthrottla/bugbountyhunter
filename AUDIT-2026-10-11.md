# BugBountyHunter — Audit & Fix Report

**Date:** 2026-10-11
**Target:** `~/bugbountyhunter/BugBountyHunter.py` (1,330 lines) + `script.py` (1,082 lines)
**Method:** static read + executed reproduction of the scan pipeline with stand-in tools
**Status:** 1 critical correctness bug found, reproduced, fixed, and verified

---

## Summary

The tool wraps three external binaries (`subfinder`, `httpx`, `nuclei`) to run
recon scans, then reports the outcome. The reporting path had a **fail-silent
defect**: when a tool existed but failed — bad API key, rate limit, no network —
the tool produced an empty output file, which the app could not distinguish from
"this target has no subdomains." It logged `SUCCESS` and recorded the scan as
`completed`.

For a beginner-oriented bug bounty tool this is the worst possible failure mode:
the user is told a clean scan finished, when in fact no scan happened. They would
conclude a target has no attack surface and move on.

## Bug 1 (CRITICAL) — failing tools reported as successful scans

**Location:** `_run_command()` (line 767) + `run_basic_scan()` (line 796) + `run_scan()` (line 706)

**Root cause:** `_run_command()` captured `returncode` and returned it, but every
caller discarded it. The code then read the (empty) output file and logged the
line count as `SUCCESS`. The scan row was written with `status='completed'`.

**Reproduction** — a tool that exists but exits non-zero:

```bash
# a stand-in tool that fails the way a rate-limited API does
cat > /tmp/faketools/subfinder <<'EOF'
#!/bin/bash
echo "error: could not reach API" >&2
exit 1
EOF
chmod +x /tmp/faketools/subfinder
```

Traced through the app's own logic:

```
_run_command(['subfinder','-d','example.com','-o',out,'-silent'])
  returncode = 1                    <- FAILURE, discarded by the caller
  stderr     = 'error: could not reach API'
subdomains = self._read_lines(out)
  subdomains found = 0
self.log(f'Found {len(subs)} subdomains', 'SUCCESS')
  *** logs: 'Found 0 subdomains' with level SUCCESS ***
status = 'completed'
  *** scan recorded as 'completed' ***
```

**Note on a wrong first read:** I initially claimed the bug was that
`_mark_scan_failed()` never ran, leaving rows stuck at `running`. Reading the
source showed `_mark_scan_failed()` does set `status='failed'` correctly — so
that claim was wrong. The real defect is narrower and worse: a tool that *runs
but fails* never raises `FileNotFoundError`, so the failure path is never
reached at all.

---

## The fix

Three changes, all verified.

### 1. `_run_command()` now reports failure

Returns an explicit `ok` flag, False when the tool could not run or exited non-zero.

```python
ok = proc.returncode in (0, -15)
return {"returncode": proc.returncode, "stdout": stdout, "stderr": stderr, "ok": ok}
```

### 2. Preflight refuses unrunnable scans

`_require_tools(scan_type)` + `_tool_usable(tool)` check every required binary
**before** a scan row is created. `_tool_usable` requires the tool to actually
execute (`--version` exit 0), not merely exist on PATH.

```python
missing = self._require_tools(scan_type)
if missing:
    self.log(f"Cannot run '{scan_type}' scan — required tool(s) not usable: "
             f"{', '.join(missing)}. Install them (see Tools tab) and retry.", "ERROR")
    return
```

### 3. Scan handlers fail loudly

`run_basic_scan()` and `run_comprehensive_scan()` now raise `RuntimeError` with
the tool's exit code and stderr instead of logging `SUCCESS` over an empty result.

`nuclei` is handled specially: it can exit non-zero when it finds nothing, so a
non-zero exit is only treated as failure if **no results file was produced**.

## Bug 2 (MODERATE) — `httpx` name collision silently shadows the recon tool

`httpx` is both a Python HTTP library CLI **and** ProjectDiscovery's HTTP probing
tool. A machine can easily end up with two `httpx` binaries on PATH, both of
them the Python one (a broken venv shim and the Python `httpx` CLI):

```
<venv>/bin/httpx   <- broken venv shim
/snap/bin/httpx    <- Python httpx CLI
```

Neither is the recon tool the scanner needs. A user following the install guide
may install the Python package, believe `httpx` is present, and run scans that
quietly probe nothing.

**Mitigation:** `_tool_usable()` now rejects both, because neither responds to
`--version` with exit 0 as ProjectDiscovery's tool does. The user gets an explicit
"required tool not usable" message instead of a false clean scan.

**Recommended further hardening (not yet applied):** resolve each tool to an
absolute path at startup and pin it, so a shadowing binary cannot be picked up
mid-run; and add a startup banner naming the resolved path of each tool.

**Independent confirmation of the diagnosis.** Extracting the original code

| Method | Symbols in ORIGINAL bytecode | What it means |

signal was captured and thrown away. The fix adds `ok` to the return value and
